00 Overview

Two modules justify the build. The rest is table stakes.

Every individual capability in the Qavia plan already exists in a more mature product. What does not exist anywhere is spec-diff-driven test maintenance (F15) combined with provider-agnostic AI that can be pinned to a local model for a client under NDA (F16). This document scores all 145 catalog features against the ten closest competitors and says which ones to build, wrap, or drop.

01 How to read this

Two different questions, both worth answering

Qavia is scoped as an internal Hyscaler platform (requirements.md §2.1), not a product for sale. So "competitor" means two things.

FramingQuestion it answersWho wins it today
Build vs buy Could Hyscaler buy this instead of building 12 phases? Katalon, KaneAI, mabl, QA Wolf
Market position If Qavia is ever commercialised, who is already there? Tricentis, LambdaTest, mabl, testRigor

Ranking below is by scope overlap, not company size. A large vendor that only does UI testing overlaps less than a small one that goes from specification to executed test.

Qavia's declared surface

spec ingest test cases + traceability code generation sandboxed execution failure root cause defect filed drift detection on spec change

No single vendor covers that whole line. Several cover one segment of it far better than Phase 4 Qavia will.

03 Competitor detail

What each one does, and where Qavia actually differs

01

LambdaTest KaneAI

The closest thing to Qavia that exists. Requirement in natural language, test authored, executed at cloud scale, code handed back in your framework, self-healing, AI root cause analysis, CI hooks. One platform, same story.

Where Qavia differs: no unit test generation, no k6 performance path, no security payload generation, no built-in defect tracker, no local-model option. Client code and specs leave the building.

Closest rival from ~$15/mo per agent, 500 agentic sessions
02

Tricentis (Tosca, Testim, Tricentis agents)

Enterprise incumbent that shipped agentic AI test creation in 2025 to 2026. Deepest coverage for SAP and packaged enterprise apps, regulated industries, model-based testing.

Where Qavia differs: cost and setup weight. Tosca is a programme, not a tool. Not a build-vs-buy threat for an internal platform. It is the ceiling if Qavia ever goes commercial upmarket.

Enterprise sales-led contracts
03

Katalon

Feature-complete across web, mobile, API and desktop, with AI-assisted generation, self-healing and visual testing built in. Has a free tier.

Where Qavia differs: Katalon does not read a requirement document or a repository and derive a test plan with requirement traceability. Tests stay in its own format.

Most likely counter-proposal free tier, pilot on Monday
04

mabl

Agentic SaaS for E2E plus API testing. Credit-metered cloud runs, self-healing, strong CI integration and reporting.

Where Qavia differs: tests live inside mabl. No repo ingest, no unit tests, no performance or security generation, no on-prem model. Phase 4 and Phase 7 should be measured against mabl, not against "does it run".

Execution benchmark ~$60/mo starter, credit-metered
05

QA Wolf

Sells an outcome, not a tool: a managed service that builds and maintains your suite and hands you standard Playwright, with coverage guarantees.

Where Qavia differs: same promise as software instead of a vendor's people, and the code and specs stay in-house. If leadership frames the problem as "we do not have enough QA capacity", QA Wolf answers it without a 12-phase build.

Substitute for the problem managed-services economics
06

testRigor

Tests written as plain English statements, generated from requirements, executed with very low maintenance. Owns the "no locators, no code" position.

Where Qavia differs: proprietary syntax, tests locked in the platform, no unit or performance testing, no repository understanding. Worth reading their output shape before finalising Qavia's case schema.

Phase 2 rival requirement to test case
07

Testsigma

Codeless natural-language authoring across web, mobile web, iOS, Android and REST API, with a large browser and device grid included.

Where Qavia differs: same lock-in pattern as testRigor and mabl. No code generation into your repository, no unit tests.

Codeless unpublished pricing, sales-led
08

Momentic

Agent-native E2E. Low-code editor, plain-English steps, intent-based self-healing locators, an autonomous agent that generates tests from the running application itself. Free self-serve entry.

Where Qavia differs: Momentic explores a running app, Qavia reads a spec or a repository. Different input, similar output. An agent that crawls the live app finds flows a spec never describes, which is worth considering as a second Phase 7 input mode.

Phase 7 reference free entry, demo-led above that
09

Qodo (formerly CodiumAI)

Repo-native. The only major tool combining automated PR review with unit test generation. Multi-agent review architecture as of Qodo 2.0 (February 2026), broad language coverage, transparent pricing.

Adjacent: Diffblue Cover does the same for Java only, using symbolic analysis rather than an LLM, producing deterministic regression tests. Higher quality inside Java, no PR review.

Pre-empts Phase 6 already in developers' IDEs
10

Keploy

Open source. Generates API test suites from OpenAPI specs, Postman collections, curl commands or recorded traffic. Container-friendly, CI-native, claims high coverage with no flake.

Adjacent: Schemathesis (property-based fuzzing from a schema), Akto (API security), Postman Postbot (in-editor assistance, not a pipeline). If Qavia's generated API tests are not clearly better than Keploy's, that slice is not paying for itself.

Free substitute API-only, no case layer, no traceability

Blunt reading

48% of the catalog (parity plus stakes) buys no advantage over a tool that already exists. Normal for a platform, but it means sequencing must protect the 19% that does. F15 and F16 are the answer to "why build this", and F16 ships in Phase 1 while F15 ships in Phase 11, dead last.

08 What we lack

Six absences. The first three get asked about in a demo

8.1

Runtime self-healing, missing entirely

mabl, testRigor, Testsigma, Katalon, KaneAI and Momentic all repair a test when a locator moves. Qavia's answer is F-6.12, a selector policy applied at generation time, plus F-7.11 flake detection after the fact. Neither repairs anything. A UI change breaks the suite and someone regenerates, which is the exact maintenance burden rivals advertise having solved.

Biggest gap add intent-based locator resolution to Phase 7, or declare it out of scope in requirements.md. Do not leave it unaddressed
8.2

Visual regression with baselines, missing

F-8.4 is a vision call on a screenshot. Applitools, Percy, mabl and Katalon have baseline capture, diff engines, ignore regions and approval workflows. Layout regressions are one of the top reasons teams buy a UI testing tool.

Unresolved wrap an open-source differ, or add it to the deferred list with a reason. It is currently neither
8.3

Cross-browser and device coverage, one container

F-7.15 is a single bundled Playwright container. Testsigma advertises 800+ browser and OS combinations and 2,000+ real devices. Even Playwright's own three engines are not stated as a matrix in the catalog.

Cheap fix Chromium, Firefox and WebKit for near zero extra work. Make it a per-project setting in Phase 7. Real devices stay out of scope
8.4

Test impact selection, missing and cheap

Launchable, Datadog and Tricentis run only the tests a diff can affect. Qavia has drift detection (F15) but no "this PR touched LoginService, run these 14 tests".

Add to Phase 6 low cost once F-6.11 and F-4.4 exist
8.5

Test management depth, partial

F5 has cases, editing and approval. No test plans, no run cycles, no manual test execution, no sign-off. TestRail, Xray and TestCollab are entire products here.

Correct to leave out note it so nobody mistakes Qavia for a test management replacement
8.6

Enterprise access plumbing, deferred

No SSO, SAML or SCIM in v1. Mobile (Appium), contract testing (Pact) and accessibility all deferred. Every top-10 rival has at least three of those.

Fine internally all six become blocking the day Qavia takes external clients

10 Plan impact

Nine things the landscape changes

From the market view

01

Breadth is the only defensible claim

Every individual capability exists in a more mature product. Nine test types on one traceable pipeline does not. Finish the thin end-to-end line before making any single test type excellent.

02

Data residency is the stronger claim

Tier-not-provider plus a local model means a client who cannot send code to a US API still gets a working platform. Open Item 6 is not a nice-to-have, it is half the differentiator.

03

Phase 6 and the API slice are the weakest build cases

Qodo and Keploy already do those, cheaply or free. Neither should be built before the end-to-end line works, and both should be benchmarked before being called done.

04

M2 needs a competitor as the baseline

"A QA engineer says the cases are usable" is a low bar. Run the same spec through testRigor or a KaneAI trial and have the reviewer compare blind. "Better than the $15/month tool" is the real bar.

05

The uncomfortable competitor is not in the table

A QA engineer with Claude Code and a repo produces Playwright and Jest tests today, no platform, no build. Qavia beats that on orchestration, sandboxing, traceability and unattended runs. Not on raw generation quality.

From the feature-level view

06

F15 is last and should not be

Phase 11 holds four of the 27 unique features and the entire "keeping tests correct" story that features.md itself calls the differentiating module. A thin F15 (F-15.1 to F-15.3, deterministic, no AI) is buildable right after Phase 2 because it needs nothing but artifacts.sha256 and a diff. Pulling it forward turns the demo from "it generates tests" into "it noticed the spec changed", which is the part nobody else does.

07

F16 is correctly early and is the business case

Phase 1 already holds ten unique features. F-16.12 and F-16.13 are what let Hyscaler take client work under NDA. Open Item 6, local models at launch or later, should be closed as at launch.

08

Cut Phase 8 to F-10.1 through F-10.5

The mocking half is commodity. Wrapping Microcks preserves the feature for a fraction of the effort.

09

Decide the Phase 7 gaps now, not in Phase 7

Self-healing, visual baselines and the browser matrix are three scope decisions that change Phase 7's size materially. Phase 7 is already tagged XL. Deciding them at the start of the phase is how XL becomes XXL.
