00 Overview

Upload a spec. Walk away. Come back to tested software.

Qavia is an internal Hyscaler platform that works like a QA engineer. It reads an API specification or a repository, writes the test cases, generates runnable test code, executes it in isolated containers, explains every failure, and files the defect. Nobody watches a progress bar.

01 How it works

The user is present for one step out of seven

Everything after Submit is a background job chain. The browser can close. Each stage is independently retryable, reports progress, and is safe to run twice — so a worker crash costs one retry, never a duplicate or a lost result.

Input

Whatever the team already has

OpenAPI or Swagger, a Postman collection, a repository, pasted requirement text, a SQL dump. Re-uploading an unchanged file does not re-run generation.

Output

Reviewable, then runnable

Test cases land first for human approval. Only approved cases become code — Supertest, Postman, Jest, Vitest, pytest, Playwright, k6.

Result

Explained, not just red

Every failure gets a root cause, a suggested fix, and the specific log lines or source location that support it. Then a defect, in one action.

02 Principles

Six rules that outrank convenience

Each is owned by a document and enforced by a mechanism. Breaking one needs an explicit decision, not a shortcut in a pull request.

01

Configuration lives in the UI, not the environment

Five bootstrap variables exist and that is the whole .env: database URL, Redis URL, encryption key, app URL, plus port and environment. Everything else is a setting in the database, edited from a screen.

Mechanism: settings registry — one declaration drives storage, validation, UI and permissions.

02

Every external platform is optional

Jira, Slack, email, GitHub, GitLab, Jenkins, S3 and every external tool server are enhancements. Unconfigured is never an error — the screen reads Not configured — using built-in.

Mechanism: capability registry — built-ins register unconditionally, adapters conditionally. See Fig 8.

03

AI runs in nine places, and deliberately nowhere else

Parsing, diffing, coverage numbers, flake detection, mock responses, bulk test data and security payloads are deterministic code. Reaching for a model there costs money and loses repeatability.

04

Agents ask for a tier, never a provider

Prompts reference reasoning, code, cheap or vision. Settings map each tier to a real model. Switching provider is a dropdown, not a deploy.

Mechanism: tier resolution through a single gateway. See Fig 7.

05

Build the built-in path first, in full

Internal defect tracker before Jira. Bundled browser before an external browser service. In-app notification before email. If a feature cannot work with an empty integrations table, it is not finished.

06

Traceability goes in at the foundation

Artifact checksums and versions, and the link from every test case back to its requirement, ship in the first phase — before anything needs them. They are what make deduplication, coverage and drift detection possible.

Mechanism: the chain in Fig 4. Retrofitting it is a rewrite.

03 Architecture

Three boundaries carry the whole design

Why the API owns persistence

One ORM, one migration history, one place invariants live. If the Python service also wrote to the database we would maintain two schemas and two sets of constraints that drift apart silently.

Why the runner is cut off

It executes model-generated code derived from uploaded files — arbitrary code execution by design. It gets a hardened runtime, no default network, and no path to anything that matters.

The confidence-score decision

The original sketch showed Confidence 92% on each failure analysis. A model asked how sure it is produces a number with nothing behind it, and showing it invites decisions it cannot support. It is replaced by a stability score derived from something measurable — or no number at all.

Capability matrix, not assumptions

Providers are not interchangeable. Each model records whether it supports tool use, vision, native structured output, and which style of prompt caching. A model without tool use cannot serve the agents that read files or drive a browser, and the interface explains why rather than letting someone pick it and hit a failure at run time.

A Test connection probe checks what actually works and overwrites what was declared. Detected beats documented.

How data residency is enforced

The cost trap worth knowing about

One specification fans out into a call per endpoint, all sharing the same prefix. Prompt caching is what makes that affordable — and providers implement it in four incompatible ways, from explicit markers to fully automatic to none at all. The same forty-endpoint spec can differ by roughly an order of magnitude in cost depending on the provider. So the estimate shown before submitting is computed from that provider's real behaviour, and a standing test asserts the shared prefix stays byte-identical. A stray timestamp in a prompt silently destroys the saving.

The one choice that needs defending: three languages

One language would be simpler. Two forces pull against that, in opposite directions.

Python, for the AI service. Getting a model to return a guaranteed shape works four different ways across providers, and the Python libraries normalise all four while every other ecosystem lags on exactly that surface. Writing and maintaining that ourselves across seven provider kinds is substantial work and a permanent source of bugs.

Go, for the API, the worker and the runner. The runner is the largest phase and a security boundary, and Docker, containerd, gVisor and Firecracker are all written in Go with first-party Go SDKs. Bounded fan-out and concurrent container runs are a semaphore rather than a queue configuration trick. sqlc checks every query against the real schema at compile time, which removes the awkward-aggregate and untyped-JSON costs an ORM would have carried. One static binary per process suits a single-VM deployment.

What it costs: three toolchains, and no shared types between the web app and the API. Four rules keep it contained:

  • The OpenAPI specification is written first and both the Go server and the TypeScript client are generated from it. Neither side hand-writes a request type.
  • The Python service is stateless and never touches the database.
  • The Go to Python boundary is the same generated-contract mechanism — a breaking change fails the build, not production.
  • The Python service holds no business logic. It runs agents; the API decides everything else.

What the query layer buys, and the one thing it costs

sqlc generates Go from real SQL checked against the migrated schema, so a column rename breaks the build rather than a request. Aggregates like requirement coverage and spend-by-provider are ordinary queries, jsonb columns unmarshal into named types, and lazy-relation N+1 is not reachable. The cost is dynamic filtering: a list endpoint with optional filters is built with squirrel inside the store, parameterised, with an integration test, because that is the one query the compiler is not checking.

Four milestones

M1 · after phase 00

The pipeline works

A user submits, walks away, and gets notified. No AI involved yet.

M2 · after phase 02

Generation is useful

A working QA engineer confirms the generated test cases are usable without substantial rewriting.

M3 · after phase 04

Execution is real

Tests generated in the platform run in the platform and match a local run exactly.

M4 · after phase 05

The loop closes

Generate, run, fail, analyse, file a defect, fix — end to end, with no external integration configured.

M2 is the real go / no-go

If a QA engineer says the generated cases are generic, wrong, or slower to fix than to write from scratch, the answer is more iteration on prompts and schemas — not building code generation on a weak foundation. Expect more than one round here and plan for it rather than treating it as slippage.

Phases 00–05 deliver the usable product: spec in, reviewed cases out, code generated, tests executed, failures explained, defects filed. Everything after that is expansion.

13 Security

Three gates, recorded before the work starts

Not during, and not after. Each blocks a specific phase because retrofitting it is far harder than building it in.

G1

Client data and outside models — blocks phase 02

Client repositories and specifications are likely covered by NDAs, so sending them to an outside service is a disclosure. Needed: a contract review on subprocessors, a per-project approval process, and a residency policy.

Cheaper than it looks — see Fig 9. A client who refuses gets a local model, so one answer no longer blocks the product.

G2

Runner isolation — blocks phase 04

The runner executes model-generated code, so plain containers are not a sufficient boundary. Needed: the hardened runtime chosen, the network policy defined, and agreement on where runner hosts sit.

G3

Target allowlisting — blocks phases 04, 07 and 09

Security probes and load tests are indistinguishable from an attack when pointed at a host you do not own. Needed: server-side allowlist enforcement, rules for rejecting internal addresses, and an approval flow before the first run against any new host.

Standing controls

  • Secrets encrypted at rest; never returned by the API, never reachable by a logger, never in a notification.
  • Every model-supplied file path resolved and confined to the workspace before any file operation.
  • Write-capable external tools kept away from the agents that read untrusted content — that intersection is where prompt injection turns into action.
  • Generated test data contains no real personal data; card numbers come only from published test ranges.
  • Audit log for login, settings change, run trigger, allowlist change, approval change and secret rotation.
