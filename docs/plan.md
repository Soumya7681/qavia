# Qavia — Implementation Plan

Phased build plan. Phases are ordered by dependency, not by calendar.

Read alongside `requirements.md` (what to build) and `ai-architecture.md` (how the
AI layer works).

---

## Milestones and Gates

Four milestones. Each is a genuine go / no-go point, not a status update.

| Milestone | After phase | Proves |
|---|---|---|
| **M1 — Pipeline works** | 0 | A user can submit, walk away, and be notified. No AI yet. |
| **M2 — Generation is useful** | 2 | A real QA engineer says the generated test cases are usable. **If this fails, stop and rethink the product, not the code.** |
| **M3 — Execution is real** | 4 | Tests generated by the platform run inside the platform and match a local run. |
| **M4 — Loop closes** | 5 | Generate → run → fail → analyse → fix, end to end, on a real project. |

### Blocking security gates

Three decisions from `requirements.md` §8 must be **recorded before** the phase
that depends on them starts. Not during. Not after.

| Gate | Blocks | Decision needed |
|---|---|---|
| **G1 — Client data and external AI** | Phase 2 | Contract review complete. Per-project approval process defined. Provider `data_residency` policy set. |
| **G2 — Runner isolation** | Phase 4 | Runtime chosen (gVisor / Firecracker). Network policy defined. Runner host placement agreed. |
| **G3 — Target allowlisting** | Phase 4, 7, 9 | Allowlist enforcement design signed off. SSRF rules defined. Security-test approval flow agreed. |

G1 has a cheaper path than it looks: because the platform is multi-provider
(`ai-architecture.md` §3.5), a client that refuses external processing gets pinned
to a local provider rather than being unsupported. The contract review still has to
happen — it just no longer blocks the whole product on one answer.

## Phase 0 — Foundation and Settings Framework

No AI. The point of this phase is that everything after it is easy.

### Backend

- Repository: `web/` (Next.js), `api/` (Go module, `cmd/api` and `cmd/worker`),
  `services/ai/` (FastAPI). No shared source package: `api/openapi/qavia.yaml` is the
  contract, and the Go server and the TypeScript client are both generated from it.
- Postgres with migrations. Tables: `users`, `sessions`, `projects`,
  `project_members`, `artifacts`, `jobs`, `job_events`, `settings`,
  `settings_audit`, `notifications`.
- Auth: local email and password, Argon2id hashing, server-side sessions, role
  guard on every route. Admin-invited users, no self-registration. Login rate
  limiting per account and per IP. No SSO in v1.
- **Settings registry.** One Go package declaring every setting: key, label,
  help text, type, default, validation, scope, secret flag, restart-required flag,
  minimum role. This is the single source of truth, and it is served to the UI at
  `GET /api/v1/settings/registry` so the settings screen cannot drift from it.
- Settings service: read with `user → project → global → default` resolution,
  write with audit row, in-memory cache with TTL and write-invalidation.
- Secret encryption: AES-256-GCM using `APP_ENCRYPTION_KEY`. Read path never
  returns plaintext — returns `{isSet, updatedAt, hint}`.
- Object storage adapter with three drivers: local disk, MinIO, S3. Configured from
  settings, not env. **Local disk is the built-in default and requires no
  configuration.**
- **Capability interfaces and built-in implementations** — the mechanism that makes
  every external platform optional (`requirements.md` §5.4). Define `Notifier`,
  `DefectTracker`, `SourceProvider`, `ObjectStore`, `BrowserDriver`, `RunTrigger`.
  Register the built-in implementation of each unconditionally at boot; register
  external adapters only when their settings are present and valid. Application
  code resolves a capability from the registry and never branches on whether a
  specific vendor is configured. Getting this in during Phase 0 is what stops
  `if (jiraConfigured)` from spreading through ten screens later.
- Built-in implementations shipped this phase: in-app `Notifier`, local-disk
  `ObjectStore`, manual + scheduled `RunTrigger`, archive-upload `SourceProvider`.
- Asynq queue. Job runner with: status transitions, progress reporting, retry with
  backoff, idempotency key, `job_events` log, and stage chaining declared in one
  `jobs/pipeline.go` rather than spread across handlers.
- A `noop` job type that sleeps and reports progress — used to prove the pipeline.
- File upload: size limit, MIME allowlist, archive-bomb rejection, SHA-256
  computed and stored.
- SSE endpoint for live job status.

### Frontend

- App shell, nav, auth pages.
- **Settings UI rendered from the registry.** Adding a setting later means adding a
  registry entry, with zero UI work. Grouped by category, secret fields masked with
  a Replace action, validation surfaced inline, restart-required badge shown.
- First-run setup wizard: creates the first admin, walks through the minimum
  settings, refuses to finish until storage is reachable.
- Project list, project create, file upload with progress.
- Job status view: stage list, progress bar, live event log via SSE.
- Notification centre.

### Settings introduced

Storage (provider, endpoint, bucket, keys, retention). SMTP. Slack. User
preferences (timezone, theme, notification channels).

### Done when

An admin completes setup entirely through the UI with only the five bootstrap
environment variables set. A user creates a project, uploads a file, submits, closes
the browser, and receives a notification when the `noop` job chain finishes. Killing
a worker mid-job results in a retry, not a lost job or a duplicate.

### Risks

Under-building the settings framework here means retrofitting it into ten screens
later. Spend the time now. The registry pattern is the whole reason the UI-first
configuration requirement is affordable.

## Phase 1 — AI Provider Layer

Still no product features. This phase makes the AI layer swappable.

### Backend / Python service

- Tables: `llm_providers`, `llm_models`, `tier_assignments`, `llm_calls`.
- Provider adapters for all seven kinds in `ai-architecture.md` §3.1. The
  `openai-compatible` adapter is the one that covers arbitrary providers.
- `LLMGateway.get_client(tier, project_id)` — resolves tier → assignment →
  provider → decrypted credentials → configured LangChain chat model, with the
  right caching strategy attached.
- Three prompt-caching strategies: explicit-breakpoint (Anthropic), passive-prefix
  (OpenAI), cache-object-lifecycle (Gemini). Selected from
  `capabilities.prompt_caching`.
- Structured output via `.with_structured_output(PydanticModel)`, plus a
  gateway-level validation and retry loop that feeds the validation error back on
  failure. Required because `prompt_only` providers will not enforce a schema.
- Accounting: every call writes an `llm_calls` row. Spend ceiling checked before the
  call, per provider and in total.
- Cross-provider fallback on retryable errors only. Records which provider actually
  served the call.
- Capability probe behind a **Test connection** button: confirms chat, tool use,
  structured output, and vision, then writes detected capabilities back over the
  declared defaults.
- Per-project provider pinning and the `external_ai_approved` flag, enforced
  server-side before any AI job is enqueued.
- Prefix-stability unit test: render the same prompt twice, assert byte-identical
  prefixes. Guards the caching invariant permanently.

### Frontend

Settings → AI → Providers, Models, Tiers, Budget. Per §6 of
`ai-architecture.md`. Health status per provider. Spend dashboard by provider,
project, and agent.

### Done when

An admin adds two providers of different kinds, assigns tiers, and a smoke-test job
runs successfully through each. Switching the `reasoning` tier from one provider to
another changes which provider serves the next job, with no deploy. A project with
`external_ai_approved = false` cannot be assigned an `external` provider — the API
rejects it.

## Phase 2 — Ingest and Test Case Generation

**Gate G1 must be closed first.** This phase decides whether the product
works.

Input scope: **OpenAPI / Swagger only.** Postman collections if time allows. No
PDFs, no repositories, no database schemas.

### Backend

- OpenAPI parsing with `pb33f/libopenapi`. Deterministic code, not AI.
  Resolve `$ref`, validate, normalize into an internal endpoint model.
- Tables: `requirements`, `test_cases`.
- Job types: `ingest`, `extract`, `design`, `dedupe`.
- Fan-out: `design` runs once per requirement, sharing a cached spec prefix.
- Deterministic fingerprint per test case from normalized
  `(method, path, assertion-kind)`. AI dedupe is the near-miss fallback only.

### AI agents

- **Extract** (`reasoning` tier, single-shot, Pydantic-locked): parsed spec →
  features, business rules, validation rules, auth model, edge cases. Each output
  carries a `source_ref` back to its location in the spec.
- **Design** (`reasoning` tier, single-shot, Pydantic-locked): one requirement →
  test cases covering happy path, each validation rule, each auth state, boundary
  values, negatives.
- **Dedupe** (`cheap` tier): given two candidate near-duplicates, same or not.

### Frontend

- Extraction review screen, shown when the project has "review before generate"
  enabled.
- Test case table: filter by requirement, category, priority, status. Inline edit.
  Bulk approve and reject. Add a case manually.
- Requirement coverage view: requirements with no test cases highlighted.
- Cost estimate before submit, computed with the assigned provider's real caching
  behaviour.

### Done when — this is M2

1. A real Hyscaler client spec goes in.
2. At least 90% of endpoints get one or more test cases.
3. **A working QA engineer reviews the output and confirms it is usable without
   substantial rewriting.**
4. Re-running generation on an unchanged spec produces no duplicate rows.
5. The same spec generates comparable output on two different providers, with the
   quality difference recorded.

Point 3 is the milestone. If a QA engineer says the cases are generic, wrong, or
would take longer to fix than to write from scratch, the answer is prompt and schema
iteration — not building Phase 3 on top of a weak foundation. Expect more than one
round of iteration here, and plan for it rather than treating it as slippage.

## Phase 3 — Code Generation and Export

- **Codegen agent** (`code` tier, one call per endpoint, cached spec prefix):
  approved test cases → Supertest suite and Postman collection.
- Table: `test_files`, recording which `test_case_ids` each file covers.
- Post-generation static validation: the file parses, imports resolve, no
  placeholder text like `// TODO` or `expect(true)`. Reject and retry on failure.
- Frontend: file tree, syntax-highlighted viewer, per-file and full-suite zip
  download, coverage badge per file.

### Done when

The exported Supertest suite runs with `npm test` against the project's staging API
and passes. A reviewer can trace any generated assertion back to the test case and
the requirement that produced it.

## Phase 4 — Execution Engine

**Gates G2 and G3 must be closed first.** Largest infrastructure phase.

### Runner

- Container runtime configurable, defaulting to gVisor.
- Pinned runner images by digest, one per framework family (Node, Playwright, k6).
  Stored as settings so an admin can update without a deploy.
- Per-run container: non-root user, read-only root filesystem, small writable
  tmpfs, CPU / memory / process / wall-clock / disk-write limits.
- Default-deny egress. Only the project allowlist plus the registries the runner
  genuinely needs.
- Metadata endpoint (`169.254.169.254`) blocked at the network layer, not in
  application code.
- One-shot: destroyed after every run, never reused.
- Runner hosts on a segment with no route to production or corporate systems.
- Every executed command logged with the run ID.

### Target safety

- Per-project host allowlist, enforced server-side before enqueue.
- Hostname resolved and checked: private, loopback, and link-local addresses
  rejected unless the project explicitly opts in for a local staging target.
- Target URL recorded on the `runs` row for after-the-fact attribution.

### Backend

- Tables: `runs`, `run_results`.
- `execute` job: materialize test files into the container, run with a JSON
  reporter, parse results, upload logs to object storage.
- Concurrency limiter honouring the settings value.
- Flake detection: re-run failures N times, count result changes, flag rather than
  report as failed.
- Cancel a running run.

### Frontend

Run button with target confirmation, live log tail, results table with pass / fail /
skipped / flaky, artifact links, run history.

### Done when — this is M3

400 tests run inside the platform against staging and produce the same pass/fail
results as the Phase 3 local export. Containers are confirmed gone afterwards. A
run targeting a non-allowlisted host is rejected at the API, and the rejection is
visible in the audit log. Attempting to reach the metadata endpoint from inside a
runner fails.

## Phase 5 — Failure Analysis

- **Analyse agent** (`reasoning` tier, LangGraph, tool-using): failing test,
  request and response, stack trace, and — when a repository is connected — the
  relevant source file and git blame.
- Table: `analyses` with reason, root cause, suggested fix, evidence, related
  commit, stability score.
- Evidence is mandatory and must point at specific log lines, response fields, or
  source locations. An analysis with no evidence is rejected and retried.
- **Stability score, not model confidence.** Derived from re-run stability across
  attempts, or blame overlap on the named file. Never a self-reported number.
- **Internal defect tracker** (`requirements.md` FR-11) — the built-in
  `DefectTracker`. Tables `defects` and `defect_comments`. Promote a failure with an
  analysis to a defect in one action. Severity, status, assignee, comments,
  duplicate linking by test case plus root cause. Defect list with filters.
  This ships here, not in Phase 10, because bug tracking must work before any
  external tracker exists.
- Frontend: analysis panel on each failure, evidence highlighted in context,
  thumbs up / down feedback stored for later prompt iteration. Defects list and
  detail view.

### Done when — this is M4

On 10 deliberately introduced failures of known cause, the analysis names the
correct root cause in at least 6, with evidence a reviewer agrees supports it.
Generate → run → fail → analyse → **file a defect** → fix works end to end on one
real project, with **no external integration configured at all**.

## Phase 6 — Repository Ingest and Unit Tests

- Git provider connection (GitHub, GitLab) via OAuth, configured from settings.
  Clone into a worker workspace. Token never enters the runner container.
- Framework detection from manifest files. Deterministic code, not AI.
- **Repo agent** (`code` tier, LangGraph, local file tools — not MCP, the repo is
  on local disk): map controllers, services, and data access; identify uncovered
  paths using the project's existing coverage report where one exists.
- **Unit test agent** (`code` tier): generate Jest, Vitest, or pytest against the
  identified gaps.
- Coverage integration: run the project's own coverage tool inside the runner,
  parse and store both line and branch coverage.
- Frontend: repository browser, coverage heat map, gap list, generate-for-selection.

### Done when

Point at a real Hyscaler repository, get runnable unit tests for the top uncovered
functions, and see measured coverage rise after running them. `requirement_coverage`
and `code_coverage` are displayed as two separate numbers, never merged.

## Phase 7 — UI Tests

- **Bundled Playwright container is the built-in browser driver.** Fully
  self-contained, no MCP server required. Build this path first and completely.
- Optional Playwright MCP server as an alternative driver, for teams that already
  run one. Bridged into LangChain tools via `langchain-mcp-adapters` so it works
  across providers. Both drivers sit behind one `BrowserDriver` interface, so the
  agent does not know which is active.
- **UI flow agent** (`code` tier, LangGraph, browser tools): drives a real browser
  through the app, discovers routes, forms, and flows by interacting, handles the
  configured auth flow, and records a flow graph. This beats reading component
  source, which misses runtime behaviour and conditional rendering.
- Playwright spec generation from the flow graph.
- Selector policy enforced in code: `data-testid` → role/label → text. CSS
  `nth-child` selectors are rejected and regenerated, not merely discouraged.
- Playwright runner: video, trace, and screenshot capture to object storage.
- Flake quarantine: a UI test that flakes more than a threshold is auto-quarantined
  and surfaced for review rather than failing every run.

### Done when

Point at a running staging app, get Playwright specs that pass three consecutive
runs, with video and trace artifacts viewable in the UI. Zero generated selectors
use positional CSS. **All of it with no MCP server configured** — the bundled
Playwright container carries the whole flow.

### Risks

Flake is the main one. Do not defer the retry policy and quarantine flag — build
them with the phase, not after complaints.

## Phase 8 — Test Data and Mock Server

- Test data generation: `brianvoe/gofakeit` seeded from the OpenAPI schema.
  Deterministic and free. AI (`cheap` tier) only for semantically tricky fields —
  a realistic Indian address, a valid GSTIN shape.
- Payment card numbers come only from published test ranges (Stripe, Visa test
  PANs). Never freshly generated Luhn-valid numbers outside those ranges.
- No real personal data, ever.
- Mock server generated from the spec: schema-valid responses, configurable delay,
  500s, timeouts, and random failure rate. Runs as its own container per project.
- Optional read-only Postgres MCP server for schema-aware data generation against a
  real database, scoped to one database with a read-only role.
- Frontend: data set preview, download as CSV / JSON / SQL, mock server controls
  with its live URL.

### Done when

Generate 100 valid and 20 deliberately invalid records from a schema, and point a
client app at the mock server and have it work.

## Phase 9 — Performance and Security Tests

**Gate G3 applies with full force.**

- k6 script generation (`code` tier) from endpoints plus a load profile chosen in
  the UI. k6 runner container, metrics parsed and charted.
- Security test generation: the agent selects which endpoints and parameters to
  target; **payloads come from a curated library** (SQLi, XSS, CSRF, JWT tampering,
  IDOR, rate limit, broken auth). The model does not invent payloads.
- Both test types are **disabled by default** and must be enabled per project by a
  QA Lead or Admin.
- First security or performance run against a new host requires an explicit
  confirmation naming that exact host.
- Findings recorded with severity, evidence, and reproduction steps.

### Done when

A k6 run produces a latency and throughput chart against staging. A security run
finds a deliberately planted SQL injection. A run against a host outside the
allowlist is rejected before any traffic is sent.

## Phase 10 — Optional External Integrations

Everything in this phase is optional and additive. The platform is
already complete without it — this phase connects it to infrastructure a team
already runs. No feature built here may become a prerequisite for anything earlier.

- MCP servers for Jira, GitHub / GitLab, and Slack, configured from Settings → MCP
  with a deny-all tool allowlist the admin opts into.
- Each adapter registers behind the capability interface established in Phase 0
  (`DefectTracker`, `Notifier`, `SourceProvider`, `RunTrigger`). Removing an
  adapter's configuration reverts cleanly to the built-in — no orphaned records,
  no broken screens.
- Runtime failure of any adapter degrades to the built-in, records the failure, and
  alerts an admin (`requirements.md` FR-10.6). A Jira outage must not lose a defect.
- **Write operations require confirmation** or an explicit per-project
  auto-write setting. An agent must not silently file twenty tickets.
- Least-privilege credentials: contents-read on GitHub unless PR creation is
  actually enabled, then contents-write on named repositories only.
- CI: GitHub Actions and Jenkins trigger a run and receive a result summary as a
  status check or PR comment.
- Jira: create a bug from a failed test with analysis and artifacts attached.
  Summary written by the `cheap` tier.
- `mcp_calls` audit table: server, tool, arguments (credential-shaped values
  redacted), result, agent, job, timestamp.

### Prompt injection

Agents read untrusted content — uploaded specs, client source, HTTP response
bodies, test logs. Any of it can contain text shaped like an instruction. An agent
that holds a write-capable MCP tool *and* reads untrusted content is the exact
combination that turns injection into action. Mitigations, all required:

- Keep write-capable tools off the agents that read untrusted content.
- Require confirmation for writes.
- Log every MCP tool call with arguments and originating job.

### Done when

A PR to a connected repository triggers a run and gets a result comment. A defect
pushes to Jira with correct fields, and the Jira key is stored back on the internal
defect. No write happens without either a confirmation or an explicit project
setting. **Then: remove every integration's configuration and re-run the full
acceptance suite from `requirements.md` §9 — including criterion 0. It must all
still pass.**

## Phase 11 — Test Maintenance

The real moat.

- Re-ingest an artifact, compare `sha256`, and **diff structurally** against the
  previous parsed version. The diff is deterministic code, not AI.
- Classify each change: endpoint added, removed, signature changed, semantics
  changed, no change.
- **Maintenance agent** (`reasoning` tier) decides, per affected test case:
  regenerate, mark stale, or delete — given the computed diff, not raw files.
- User approves the proposal before anything is applied.
- History retained via `superseded_by`. A wrongly-deleted case can be restored.
- Scheduled re-check: poll connected specs and repositories, notify on drift.

### Done when

Change a required field in a spec, re-upload, and the system flags **exactly** the
affected test cases and nothing else. Accept the diff, and those cases regenerate
correctly. Reject it, and nothing changes. Restore a deleted case successfully.

## Relative Effort

No durations here. Effort is expressed relative to the other phases so scope can be
compared without committing to a calendar.

| Phase | Effort | Driver of the effort |
|---|---|---|
| 0 — Foundation and settings | L | Settings registry and capability interfaces are built once and depended on everywhere |
| 1 — AI provider layer | M | Seven provider adapters, three caching strategies |
| 2 — Ingest and test cases | L | Quality iteration, not code volume. Expect several rounds |
| 3 — Code generation | S | Thin layer over Phase 2's output |
| 4 — Execution engine | XL | Security boundary. Isolation, egress control, artifact capture |
| 5 — Failure analysis | M | Analysis agent plus the defect tracker |
| 6 — Repo and unit tests | L | Repo comprehension agent, framework detection, coverage integration |
| 7 — UI tests | XL | Browser driving, selector stability, flake handling |
| 8 — Test data and mocks | M | Mostly deterministic code |
| 9 — Performance and security | L | Payload library and approval controls |
| 10 — Optional integrations | M | Adapters behind existing interfaces |
| 11 — Maintenance and drift | L | Structural diffing and the approval flow |

Phases 0 through 5 deliver a genuinely useful product: spec in, reviewed test cases
out, code generated, tests executed, failures explained, defects filed. That is the
point at which internal teams can start using it daily. Everything after Phase 5 is
expansion.

Phases 4 and 7 are the two largest and both carry the most risk — one is a security
boundary, the other fights flake. Neither should be scheduled as if it were an
average phase.

---

## Sequencing Rules

1. **Do not start Phase 3 before M2 passes.** Building code generation on test
   cases a QA engineer would not use multiplies wasted work.
2. **Do not start Phase 4 before G2 and G3 are closed.** The runner is a security
   boundary. Retrofitting isolation into a working runner is harder than building
   it isolated.
3. **Phases 6 through 9 can reorder** based on which internal team needs what
   first. They have no hard dependency on each other.
4. **Phase 11 depends on Phase 2's traceability**, which is why
   `artifacts.sha256`, `artifacts.version`, and `test_cases.requirement_id` go in
   during Phase 0. Retrofitting them is a rewrite.
5. **Never let the AI layer leak.** Every phase that adds an agent uses
   `LLMGateway.get_client(tier)`. No agent names a provider or model. That rule is
   what keeps provider switching a settings change forever.
6. **Build the built-in path first, in full, in every phase.** External platforms
   are additive only. No phase may ship a feature whose only implementation is an
   external integration. Concretely: the internal defect tracker before Jira, the
   bundled Playwright container before Playwright MCP, in-app notification before
   SMTP or Slack, archive upload before GitHub OAuth, local disk before S3. If a
   feature cannot work with an empty integrations table, it is not done.
