# Qavia Frontend Work

Every frontend task, in build order. Track B of [work.md](./work.md).

**This track is blocked until `BE-X.1` (contract freeze) is signed off.** See
[work-backend.md](./work-backend.md) for that task and `work.md` §2 for why the
order is sequential.

By the time this track starts, four things already exist and are the foundation of
every task below:

| | Artifact | From |
|---|---|---|
| S1 | Complete, frozen `api/openapi/qavia.yaml` with examples | `BE-X.1` |
| S2 | `GET /api/v1/settings/registry` serving every setting as JSON Schema | `BE-0.16` |
| S3 | SSE streams for job status and run logs | `BE-0.24`, `BE-4.11` |
| S4 | Error envelope `{ code, message, details? }` and `docs/error-codes.md` | `BE-0.3`, `BE-X.4` |

Plus `make mock` (`BE-X.3`) and `make seed` (`BE-X.2`), so no screen ever waits on
a running backend.

## Standing rules for every task

These are not repeated per task. A PR that breaks one is not done.

1. **No hand-written request or response type.** The client is generated from
   `qavia.yaml`. A field the spec does not describe does not exist
   (`backend-standards.md` §10).
2. **No database credentials, no queue access, no server actions that reach around
   the API.** Every read and write goes through the Go API, so there is exactly one
   place authorisation is enforced.
3. **Server components for initial render, TanStack Query for anything that changes
   after load** (`tech-stack.md` §2). No data fetching in client components except
   through TanStack Query.
4. **Branch on `error.code`, never on the message string.**
5. **Four states per screen, always:** loading, empty, error, and populated. An
   empty state says what to do next, not "no data".
6. **Long operations return `202` with a job ID.** No screen waits on a synchronous
   generate or run; it subscribes to the job.
7. **Secrets are never pre-filled.** A configured secret renders as
   `{ isSet, updatedAt, hint }` with a Replace action.
8. **An unconfigured integration reads "Not configured, using built-in X" with a
   link to configure it.** Never an error, never a broken screen
   (`requirements.md` §5.4).
9. **All timestamps display in the user's configured timezone**, stored UTC
   (NFR-7). One formatting helper, used everywhere.
10. **Every list is cursor paginated** using `?limit=&cursor=` and `nextCursor`.

# FE-S  Setup

### FE-S.1  Next.js scaffold

**Requires** BE-X.1.

1. Next.js App Router in `web/`, TypeScript strict mode, pnpm.
2. Route groups: `(auth)` for login and invite acceptance, `(app)` for the
   authenticated shell, `(setup)` for the first-run wizard.
3. `next.config` with the API base URL from a build-time public variable only.
   **No secret ever reaches the browser bundle.**
4. Absolute imports, ESLint, Prettier, and the lint step wired into `make lint`.

**Done when** the app builds, runs against `make mock`, and CI runs its lint and
type check.

### FE-S.2  Design system

**Requires** FE-S.1.

1. Tailwind configured with the project's tokens: colour, spacing, radius,
   typography scale. Define the tokens once; do not scatter literals.
2. shadcn/ui components **copied into the repo**, not installed, so they can be
   modified. The settings UI needs variants no library ships.
3. Light and dark theme, driven by the user's theme setting, with a system default.
4. `cn()` helper. Repeated class strings are extracted into components, never into
   `@apply`.
5. Base primitives first: Button, Input, Select, Checkbox, Dialog, Sheet, Table,
   Tabs, Badge, Toast, Tooltip, Skeleton, EmptyState, ErrorState.

**Done when** every primitive renders in both themes and the two shared state
components (EmptyState, ErrorState) exist before any screen is built.

### FE-S.3  Generated API client

**Requires** BE-X.1. **Seam S1.**

1. `openapi-typescript` plus `openapi-fetch`, generated by `make gen`, output
   committed.
2. A thin wrapper adding credentials, the correlation ID header, and error
   normalization into a typed `ApiError { code, message, details, status }`.
3. TanStack Query configured: query key convention, default stale times, retry only
   on network errors, and global handling for 401 (redirect to login) and 403
   (permission screen).
4. CI fails on a stale generated client.

**Done when** an endpoint added to the spec appears in the client after `make gen`,
and a hand-written fetch call anywhere fails review.

### FE-S.4  Auth and route guards

**Requires** BE-0.10, FE-S.3. **Seam S5.**

1. Session cookie handled by the browser; the app never stores a token.
2. Server-side guard in the `(app)` layout: fetch `GET /me`, redirect to login when
   unauthenticated.
3. Role-aware rendering helper. **This is presentation only.** The API is the
   authority, and the UI never assumes an action is permitted because a button is
   visible.
4. Project membership guard for project-scoped routes.
5. A 403 from any call renders a clear "you do not have access" state, not a blank
   page.

**Done when** every route is guarded through the layout rather than per page, and a
role change takes effect on the next request.

### FE-S.5  Shared data conventions

**Requires** FE-S.3.

1. A `useCursorList` hook wrapping cursor pagination for every list screen.
2. A `useJob(jobId)` hook: fetch state, subscribe to SSE, invalidate the affected
   queries on completion.
3. A `useSSE` primitive: reconnect with backoff, `Last-Event-ID` resume, clean
   teardown on unmount.
4. Optimistic update helper for inline edits, with rollback on error.
5. Timezone and number formatting helpers, reading the user's settings.

**Done when** all five are covered by Vitest tests, because every screen depends on
them.

### FE-S.6  Testing setup

**Requires** FE-S.2.

1. Vitest plus Testing Library. Test behaviour, not implementation.
2. Playwright for end to end, running against `make mock` in CI and against a real
   stack locally.
3. Mock Service Worker for component-level API stubbing, seeded from the spec
   examples so stubs cannot drift from the contract.

**Done when** one component test and one end-to-end test run in CI.

# FE-0  Shell and Foundation

### FE-0.1  App shell

**Requires** BE-0.9, BE-0.10 | **Endpoints** `GET /me`

1. Sidebar navigation, project switcher, user menu, theme toggle.
2. Breadcrumbs derived from the route, not hand-maintained.
3. Global toast host and a global error boundary that renders the incident ID
   returned by the API.
4. Responsive down to a laptop width. This is an internal tool; mobile is not a
   target, but nothing should be unusable at 1280px.
5. Default landing page from the user's setting.

**Done when** navigation, the project switcher, and the error boundary all work
against the mock.

### FE-0.2  Login and account

**Requires** BE-0.10, BE-0.11 | **Endpoints** `POST /auth/login`, `POST /auth/logout`, `POST /auth/accept-invite`, `POST /auth/change-password`

1. Login form, React Hook Form plus Zod.
2. **Identical error for wrong password and unknown account.** Do not leak account
   existence in copy, timing, or field-level validation.
3. Lockout state renders a specific message with the remaining duration, driven by
   the error code.
4. Invite acceptance: set a display name and a password, with the password rules
   from the registry rather than hardcoded.
5. Change password, and sign out.

**Done when** every auth error code from the catalog renders a distinct, useful
message, and lockout is unmistakable.

### FE-0.3  First-run setup wizard

**Feature** F-1.10 | **Requires** BE-0.28 | **Endpoints** `GET /setup/status`, `POST /setup/admin`

1. Detect the setup state on load and route into the wizard when required.
2. Steps: create the first admin, confirm storage is reachable, optionally add an AI
   provider.
3. **Only genuinely required settings block progress.** Everything else is visibly
   skippable with "you can add this later".
4. Storage step shows the reachability probe result and refuses to finish until it
   passes.
5. The AI provider step is marked "required before AI jobs can run", not "required
   to finish".
6. After the wizard, the route is permanently unreachable.

**Done when** a fresh install reaches a working logged-in admin entirely through the
UI with only the six bootstrap environment variables set. This is acceptance
criterion 1.

### FE-0.4  Settings UI rendered from the registry

**Feature** F-1.6 | **Requires** BE-0.16 | **Seam S2** | **Endpoints** `GET /settings/registry`, `GET /settings`, `PUT /settings`, `DELETE /settings/{key}`

The single highest-leverage screen in the app. Built once, it costs nothing per
setting forever.

1. Fetch the registry, group entries by category, and **render controls from the
   declared type**. No screen hardcodes a setting key.
2. Convert each entry's JSON Schema to Zod **at runtime** for React Hook Form, so
   client and server validation come from one declaration
   (`tech-stack.md` §11).
3. Control mapping: string, int, number, bool, enum, string list, object, secret,
   duration. Add a control type by extending this map, not by writing a screen.
4. Secrets render as `{ isSet, updatedAt, hint }` with a Replace action. Never
   pre-filled, never readable.
5. Show, per field, which scope the effective value came from (user, project,
   global, or default) and offer "reset to inherited".
6. Restart-required entries carry a badge and a warning on save.
7. Fields above the caller's minimum role are hidden, and the API enforces it
   anyway.
8. Validation errors surface inline against the field, from the API response
   `details`.

**Done when** a setting added to the Go registry appears, validates, and saves with
**zero frontend changes**. Prove it by adding one during review.

### FE-0.5  Projects

**Feature** F-1.4 | **Requires** BE-0.25 | **Endpoints** `/projects`, `/projects/{id}`, `/projects/{id}/members`, `/projects/{id}/archive`

1. Project list with search and cursor pagination.
2. Create dialog: name, description, and **test type selection**. Unimplemented
   types render **disabled with a "coming soon" label, not hidden** (F-3.12).
3. Project detail shell with the tab structure later phases fill: Overview,
   Requirements, Test Cases, Files, Runs, Defects, Settings.
4. Members: add, change role, remove.
5. Archive, with confirmation. An archived project renders read-only with a banner,
   and every mutating control is disabled with the reason.

**Done when** a QA Engineer sees only their projects, a QA Lead sees all, and an
archived project cannot be mutated from any control.

### FE-0.6  Upload and submit

**Feature** F-3.10, F-3.11 | **Requires** BE-0.26, BE-0.22 | **Endpoints** `POST /projects/{id}/artifacts`, `POST /projects/{id}/jobs`

1. Drag and drop plus file picker, with a real progress bar from the upload stream.
2. Client-side size and type pre-check for fast feedback, **with the server as the
   authority**. Never present the client check as the guarantee.
3. Duplicate upload renders "identical file already uploaded, generation skipped"
   with a link to the existing artifact, not an error.
4. A changed file for the same logical artifact shows the new version number and
   links to the previous one.
5. Submit returns `202` and routes straight to the job view. **The user can close
   the browser** and the copy should say so.
6. Rejected upload errors are specific: too large, wrong type, archive bomb.

**Done when** a user uploads, submits, closes the tab, and the work continues, with
every rejection reason distinctly explained.

### FE-0.7  Job status and event log

**Feature** F-2.2, F-2.3 | **Requires** BE-0.22, BE-0.24 | **Seam S3** | **Endpoints** `GET /jobs/{id}`, `GET /jobs/{id}/events` (SSE)

1. Stage list with per-stage status, a progress bar, and elapsed time.
2. Live event log over SSE using `useSSE`. A late joiner gets history then live
   output.
3. Reconnect with backoff and a visible "reconnecting" state. Never silently stop
   updating.
4. Reflect a state change within 5 seconds (NFR-3).
5. Terminal states: succeeded with a link to the result, failed with the error and
   a retry action where retry is permitted, cancelled.
6. Cancel button where the job is cancellable.
7. Clean teardown on unmount. A leaked EventSource is a real bug here.

**Done when** two tabs watching one job both update live, a network drop recovers
without a refresh, and unmounting closes the stream.

### FE-0.8  Notification centre

**Feature** F-14.1 to F-14.5 | **Requires** BE-0.19 | **Endpoints** `/notifications`, `/notifications/{id}/read`, `/notifications/read-all`, `/notifications/unread-count`

1. Bell with an unread count, panel with the list, mark one or all read.
2. Every notification deep links to its result and the link works.
3. Per-channel toggles in user settings, rendered from the registry.
4. **Unconfigured channels show "Not configured" with a link to settings, never an
   error.** In-app is always present and cannot be disabled into silence.

**Done when** a job completing produces a notification with a working deep link on a
system with SMTP and Slack unconfigured, and nothing on the screen looks broken.

### FE-0.9  Audit log viewer

**Feature** F-17.1 | **Requires** BE-0.27 | **Endpoints** `GET /audit`

1. Admin-only table with filters by actor, action, date range, and subject.
2. Detail drawer showing the recorded payload.
3. Cursor paginated. Never render an unbounded list.

**Done when** every audited action is findable and no entry displays a secret.

# FE-1  AI Settings

**Requires** BE-1.13, BE-1.10, BE-1.14. Screens defined in
`ai-architecture.md` §6.

### FE-1.1  Providers

**Feature** F-16.1, F-16.2, F-16.5 | **Endpoints** `/ai/providers`, `POST /ai/providers/{id}/test`

1. List with health status per provider and when it was last checked.
2. Add and edit: kind, non-secret config, credentials, data residency.
3. **The credential form changes shape by kind** (`ai-architecture.md` §3.3).
   Anthropic takes a key; Bedrock takes keys **or** `use_instance_role` with no
   keys; Vertex takes service account JSON; `openai-compatible` takes base URL, an
   optional key, and optional custom headers.
4. Offer `use_instance_role` as the default Bedrock option when the API reports the
   platform is on EC2 or ECS.
5. **Test connection** runs the probe, shows what was detected, and explains that
   detected capability overwrites declared capability.
6. Deleting a provider referenced by a tier assignment is refused with the
   assignment named. Render that as guidance, not a stack trace.

**Done when** all seven provider kinds can be added and tested from the UI with no
deploy, and every credential field is write-only.

### FE-1.2  Models

**Feature** F-16.4, F-16.11 | **Endpoints** `/ai/models`

1. Per provider: enabled models, display name, tiers the model may serve,
   capabilities, prices, token limits.
2. Capability matrix editable, with detected values visually distinguished from
   declared ones.
3. **Prices editable in the UI.** Pricing changes must never need a deploy.
4. A model with `vision: false` cannot be offered for the `vision` tier, and a model
   with `tool_use: false` cannot serve the tool-using agents. **Show the reason**
   rather than silently hiding the option.

**Done when** an unusable model explains why it is unusable instead of disappearing.

### FE-1.3  Tiers

**Feature** F-16.3 | **Endpoints** `/ai/tiers`

1. Map `reasoning`, `code`, `cheap`, and `vision` to a model, an optional fallback
   model, and an effort level where supported.
2. Global scope, with a per-project override surface in project settings.
3. An unassigned tier is shown as an explicit warning with the consequence spelled
   out: "AI jobs using this tier will be refused at submit."
4. Explain fallback in one line: it handles availability errors, not refusals.

**Done when** switching the `reasoning` tier from one provider to another changes
which provider serves the next job, with no deploy.

### FE-1.4  Budget

**Feature** F-16.10 | **Endpoints** `/ai/budget`

1. Monthly ceiling per provider and in total. Behaviour on reaching it: block or
   warn.
2. Current spend against the ceiling, with a clear visual threshold.
3. When a ceiling is blocking, every affected submit action explains it at the point
   of submission, not only here.

**Done when** exceeding a ceiling produces a specific, actionable message wherever a
job would be enqueued.

### FE-1.5  Spend dashboard

**Feature** F-12.7 | **Requires** BE-1.14 | **Endpoints** `GET /ai/spend`

1. Recharts breakdowns by provider, by project, and by agent, over a date range.
2. Tokens and cost shown separately, with cache-read tokens broken out, because
   caching is the whole cost story.
3. Table view under the charts, cursor paginated.

**Done when** the chart totals reconcile with the table and with the API.

# FE-2  Generation Review

The screens that decide whether M2 is judged fairly. If review is painful, good
generation looks bad.

### FE-2.1  Extraction review

**Feature** F-4.3 | **Requires** BE-2.6 | **Endpoints** `/projects/{id}/requirements`

1. Shown when the project has "review before generate" enabled; the chain is paused
   and the screen says so.
2. List extracted requirements grouped by kind: feature, business rule, validation
   rule, auth, edge case.
3. **Every item links to its source location** in the artifact. Render the spec
   excerpt inline; do not make the user go and find it.
4. Edit, delete, and add before approving.
5. Approve continues the chain and returns the user to the job view.

**Done when** a reviewer can accept or correct 40 endpoints' worth of extraction
without leaving the screen, and every item's source is one click away.

### FE-2.2  Test case table

**Feature** F-5.5 | **Requires** BE-2.10 | **Endpoints** `/projects/{id}/test-cases`, `PATCH /test-cases/{id}`, `POST /test-cases`, `POST /test-cases/bulk-status`

The most heavily used screen in the product. Treat it like a tool, not a report.

1. Virtualised table, cursor paginated, filters for requirement, category,
   priority, and status. Filter state lives in the URL so a view is shareable.
2. Columns: title, requirement, category, priority, status, and a steps preview.
   Expand for preconditions, steps, and expected result.
3. **Inline edit with optimistic update and rollback on error.**
4. Multi-select with bulk approve and bulk reject, respecting the API's batch cap
   and reporting partial failure honestly.
5. Add a case manually with the same form used for editing.
6. Keyboard navigation: arrow keys, `a` to approve, `r` to reject, `e` to edit.
   Reviewing 400 cases with a mouse is the difference between usable and not.

**Done when** a QA engineer can triage 400 cases in one sitting, and an edit that
fails server-side visibly reverts.

### FE-2.3  Traceability view

**Feature** F-5.6 | **Requires** BE-2.10, BE-2.11

1. From a test case, navigate to its requirement and to the source location.
2. From a requirement, see every case it produced.
3. Deduplicated and superseded cases are visible with their history, not hidden.

**Done when** any assertion can be traced back to the requirement and the spec line
that produced it, in two clicks.

### FE-2.4  Requirement coverage

**Feature** F-12.2 | **Requires** BE-2.11 | **Endpoints** `GET /projects/{id}/coverage/requirements`

1. One number, clearly labelled **Requirement coverage**, with its definition on
   hover.
2. **Requirements with no test cases are listed and highlighted**, which is the
   actionable part.
3. Generate-for-selection on uncovered requirements.
4. **Never combined with code coverage into one number** (FR-7.2). They sit side by
   side with distinct labels, and code coverage is absent with a reason when no
   repository is connected.

**Done when** the two coverage numbers can never be mistaken for one another.

### FE-2.5  Cost estimate before submit

**Feature** F-5.7 | **Requires** BE-2.12 | **Endpoints** `POST /projects/{id}/estimate`

1. Show the estimate in the submit dialog, before the user commits.
2. Show the assumptions: endpoint count, calls, cached prefix tokens, provider,
   caching mechanism.
3. **Label it an estimate**, and state that the same spec costs very differently on
   a provider without prompt caching.
4. If the estimate would breach the budget ceiling, block or warn per the configured
   behaviour, with the reason.

**Done when** two providers show materially different estimates for the same spec
and the difference is explained on screen.

### FE-2.6  Project dashboard

**Feature** F-12.1 | **Requires** BE-2.11, BE-4.14 | **Endpoints** `GET /projects/{id}/dashboard`

1. Counts: requirements, generated tests, passed, failed, skipped, flaky.
2. Last run time and current job status, live.
3. Recent failures with direct links to their analysis (fills in at `FE-5`).
4. Primary actions: Generate, Run, View Reports, Export.
5. Every panel handles its own empty state; a new project shows next steps, not
   zeros.

**Done when** a brand new project's dashboard is useful rather than a grid of
zeroes.

# FE-4  Runs

### FE-4.1  Run trigger

**Requires** BE-4.7, BE-4.9 | **Endpoints** `POST /projects/{id}/runs`

1. Run dialog: which test files or suites, and the target.
2. **The target host is displayed prominently and must be confirmed.** This is a
   safety control, not a formality.
3. A non-allowlisted host is refused by the API; render
   `target_host_not_allowed` with the fix: which host, and where to add it.
4. No target configured renders a specific state explaining that generation works
   and execution does not, with a link to project settings (F-3.13).
5. Returns `202`; route to the run view.

**Done when** it is impossible to trigger a run without seeing the exact host that
will be hit.

### FE-4.2  Run list and detail shell

**Requires** BE-4.14 | **Endpoints** `/projects/{id}/runs`, `/runs/{id}`

1. List with status, target, trigger, duration, and counts, cursor paginated.
2. Detail shell with tabs: Results, Logs, Artifacts.
3. Status badges covering passed, failed, skipped, **flaky**, cancelled, and
   running.

**Done when** flaky is visually distinct from failed everywhere it appears.

### FE-4.3  Live log tail

**Feature** F-7.9 | **Requires** BE-4.11 | **Seam S3** | **Endpoints** `GET /runs/{id}/logs` (SSE)

1. Virtualised log viewer with follow-tail, pause on scroll up, and resume.
2. Search within the buffer and level filtering.
3. Reconnect handling identical to `FE-0.7`, reusing `useSSE`.
4. On completion, switch to the stored full log from object storage without the user

5. A dropped-lines marker when the server applied backpressure. Never pretend the

**Done when** a 100,000-line run scrolls smoothly and a mid-run reconnect loses

### FE-4.4  Results table

**Requires** BE-4.9 | **Endpoints** `/runs/{id}/results`

1. Filter by status, file, and requirement. Group by file or by requirement.
2. Row expands to show duration, attempts, and error output.
3. **Flaky rows show every attempt and how the result changed**, which is the whole
   point of detecting flake instead of reporting failure.
4. Direct links to logs, screenshots, videos, and traces.
5. Compare against the previous run: newly failing, newly passing, still failing.

**Done when** "what changed since the last run" is answerable without leaving the
page.

### FE-4.5  Cancel and artifacts

**Requires** BE-4.12, BE-7.5 | **Endpoints** `POST /runs/{id}/cancel`, `/runs/{id}/artifacts`

1. Cancel with confirmation, and a clear cancelling state until the container is
   reaped.
2. Artifact list with type, size, and download. Signed URLs, expiry handled quietly

3. Partial results from a cancelled run are shown and labelled as partial.

**Done when** cancelling is unambiguous and partial results are never mistaken for
complete ones.

### FE-4.6  Run history and trends

**Feature** F-12.6 | **Requires** BE-4.14 | **Endpoints** `GET /projects/{id}/runs/trend`

1. Recharts: pass rate over time, duration over time, flake count over time.
2. Click a point to open that run.
3. Empty state before there is history, not an empty chart frame.

**Done when** a regression is visible on the chart and one click away from its run.

# FE-5  Analysis and Defects

### FE-5.1  Analysis panel

**Feature** F-9.1, F-9.5 | **Requires** BE-5.2, BE-5.3 | **Endpoints** `GET /run-results/{id}/analysis`

1. Panel on each failure: reason, probable root cause, suggested fix.
2. **Evidence highlighted in context.** A cited log line renders inside the log with
   the range highlighted; a cited response field renders inside the response body; a
   cited source location renders the file at that line.
3. Related commit shown when a repository is connected, linked where the provider
   supports it.
4. An analysis that is still running shows progress, not a blank panel.

**Done when** every evidence reference is clickable and lands exactly where it
points.

### FE-5.2  Stability score presentation

**Feature** F-9.4 | **Requires** BE-5.4

1. Show the score **only when the API returns one**.
2. State the signal it came from: re-run stability, or blame overlap.
3. **When the API returns null, show nothing.** No placeholder, no "unknown
   confidence", no invented number.
4. Never label it "confidence". It is a stability score derived from measurements.

**Done when** a null score renders as absence, and no copy anywhere implies model
self-assessment.

### FE-5.3  Defect tracker

**Feature** F-9.7 to F-9.10 | **Requires** BE-5.5 to BE-5.7 | **Endpoints** `/defects`, `POST /run-results/{id}/promote`, `/defects/{id}/comments`

1. **Promote to defect in one action** from a failure that has an analysis, with the
   fields pre-filled.
2. Defect list with filters by project, severity, status, and assignee, cursor
   paginated.
3. Detail view: description, severity, status, assignee, comment thread, and full
   traceability to the run result, test case, requirement, analysis, and artifacts.
4. Duplicate handling: a linked duplicate shows the parent defect and its

# FE-Q  Cross-Cutting Quality

Run these continuously, not at the end. Each one is cheap while there are ten
screens and expensive at forty.

### FE-Q.1  State coverage audit

1. Every screen has loading, empty, error, and populated states.
2. Empty states say what to do next and link to it.
3. Error states render `error.code` distinctly and offer a real action, never a bare
   "something went wrong".
4. Skeletons match the shape of the eventual content so the layout does not jump.

**Done when** an audit walks every route in all four states with no gaps.

### FE-Q.2  Permissions audit

1. Walk the app as each of the four roles: Admin, QA Lead, QA Engineer, Viewer.
2. **Viewer sees no mutating controls anywhere.**
3. A 403 from any call renders a clear message, never a blank page or a crash.
4. Hidden controls are convenience only; the API is the authority and is tested
   separately.

**Done when** all four walkthroughs are clean and recorded.

### FE-Q.3  Timezone and formatting

1. Every timestamp renders in the user's configured timezone (NFR-7).
2. Relative times ("5 minutes ago") carry the absolute time on hover.
3. Durations, byte sizes, token counts, and currency all use one formatting helper.

**Done when** switching the timezone setting changes every displayed timestamp.

### FE-Q.4  Accessibility

1. Keyboard navigable throughout, with a visible focus ring.
2. Dialogs trap focus and restore it on close.
3. Colour is never the only signal: pass, fail, and flaky carry a shape or a label
   too.
4. Live regions announce job and run status changes.

**Done when** the primary flow, from login to reviewing a failure, is completable by
keyboard alone.

### FE-Q.5  End-to-end suite

1. Playwright covering: setup wizard, login, create project, upload, submit, watch
   the job, review cases, generate code, run, read the analysis, file a defect.
2. Runs against `make mock` in CI, and against a real stack nightly.
3. Includes the zero-integration walkthrough from `FE-10.3`.

**Done when** the suite is green in CI and catches a deliberately broken screen.

### FE-Q.6  Performance pass

1. Virtualise every long list: test cases, results, logs, audit.
2. Server components carry the initial render; keep the client bundle small. No
   editor, no client-side highlighting library.
3. Confirm SSE connections are torn down on unmount, with no leaked EventSource
   after navigating away.
4. Measure the heaviest screens (test case table at 5,000 rows, log viewer at
   100,000 lines) and record the numbers.

**Done when** the two heaviest screens are measured and the numbers are recorded in
this file.
